# Spotify Customer Support AI Agent

An explainable customer-support AI pipeline built around historical Spotify support interactions.

The system combines TF-IDF retrieval, a hosted LLM, deterministic escalation rules, and an evaluation framework covering intent classification and reply quality.

---

## 1. Project Overview

The agent takes a customer's current message and optional conversation context and produces:

1. A customer-support intent
2. A concise support reply
3. An escalation decision
4. A reason for that decision
5. Three similar historical Spotify support cases used as evidence

The system does not train a new neural model. It uses a pretrained LLM through the Groq API and augments it with retrieval from historical Spotify support interactions.

### Pipeline

Customer message + conversation context
                |
                v
        TF-IDF retrieval
                |
                v
    Top 3 historical Spotify cases
                |
                v
             Groq LLM
                |
          +-----+-----+
          |           |
          v           v
       Intent       Reply
          |
          v
Deterministic escalation policy
          |
          v
   AUTO_HANDLE / ESCALATE

## 2. Dataset

The project uses the Kaggle Customer Support on Twitter dataset (`twcs.csv`).

The pipeline selects Spotify support interactions and constructs customer-to-Spotify support cases with bounded conversation context.

The derived retrieval corpus is:

`results/spotify_cases.csv`

The construction script is:

`src/build_spotify_cases.py`

The original dataset is stored at:

`data/twcs.csv`

## 3. Human Annotation

A 200-example Spotify dataset was manually labelled for intent using the project's nine-category intent taxonomy.

The final intent categories are:

* `PLAYBACK_OR_APP_ISSUE`
* `SUBSCRIPTION_OR_PAYMENT`
* `ACCOUNT`
* `FEATURE_OR_UI`
* `CONTENT_OR_CATALOG`
* `PROMOTION_OR_EVENT`
* `PRIVACY_OR_DATA`
* `SUPPORT_CHANNEL_OR_LANGUAGE`
* `OTHER`

The annotation work was completed in batches and then merged into the final gold annotation set. Quality-control and merge processing were performed before the development/test split was created.

The completed gold annotations are stored in:

`results/spotify_gold_annotations.csv`

The annotation and merge scripts are:

* `src/annotate_spotify.py`
* `src/merge_annotations.py`

The 200 labelled cases form the evaluation pool. They were split into development and held-out test sets only after the gold annotations were finalized.

## 4. Development / Test Split

The 200 labelled cases are divided into:

* 150 development cases
* 50 held-out test cases

The split uses `StratifiedGroupKFold` with:

* 4 folds
* `random_state=42`
* `customer_id` as the grouping variable

Grouping by customer prevents the same customer from appearing in both development and test sets.

The split is generated by:

`src/create_eval_split.py`

The resulting files are:

* `results/spotify_dev.csv`
* `results/spotify_test.csv`

The 50-case test set used for the final reported evaluation is held out and should not be used for prompt or policy tuning.

## 5. Agent Architecture

### Retrieval

The retriever uses:

* TF-IDF
* unigram and bigram features
* cosine similarity
* top-3 historical cases

Implementation:

`src/retriever.py`

The retrieval corpus is loaded from:

`results/spotify_cases.csv`

### LLM

The final agent uses the Groq API with:

`openai/gpt-oss-20b`

The LLM is instructed to return a structured JSON object containing:

* `intent`
* `reply`

Implementation:

`src/groq_client.py`

### Agent

The main pipeline is implemented in:

`src/agent.py`

It combines retrieval, LLM classification/reply generation, and deterministic escalation.

## 6. Escalation Policy

Escalation is deterministic and does not depend on an additional LLM decision.

The current policy is:

| Condition                                      | Action        |
| ---------------------------------------------- | ------------- |
| `PRIVACY_OR_DATA`                              | `ESCALATE`    |
| `ACCOUNT` + configured account-specific action | `ESCALATE`    |
| `OTHER`                                        | `ESCALATE`    |
| Other clear intents                            | `AUTO_HANDLE` |

Configured account-specific actions include requests involving:

* changing email/password
* deleting or closing an account
* refunds
* chargebacks
* cancelling subscriptions
* restoring or recovering an account

Implementation:

`src/escalation_policy.py`

The evaluated 50-case output is:

`results/escalation_test_outputs.csv`

In the final 50-case run:

* 39 cases -> `AUTO_HANDLE`
* 11 cases -> `ESCALATE`

This is an action distribution, not an escalation accuracy measurement, because the human dataset does not contain human-labelled escalation outcomes.

## 12. Failure Analysis

The final 50-case evaluation identified five recurring failure modes.

### 1. Context-dependent short messages

Short follow-up messages are difficult to classify when their intent depends on earlier conversation context.

Examples:

- Case 4: `Okay. Thankyou.` → predicted `OTHER`, gold `SUBSCRIPTION_OR_PAYMENT`
- Case 64: `All sorted now! But thanks for the response :)` → predicted `OTHER`, gold `ACCOUNT`
- Case 70: `Ok, thanks.` → predicted `OTHER`, gold `PLAYBACK_OR_APP_ISSUE`
- Case 137: `Thank you` → predicted `OTHER`, gold `ACCOUNT`

**Hypothesis:** These messages contain little standalone semantic information. Correct classification depends heavily on preceding conversation context.

### 2. FEATURE_OR_UI vs CONTENT_OR_CATALOG ambiguity

Examples:

- Case 71: an iTunes-related request was classified as `CONTENT_OR_CATALOG` instead of `FEATURE_OR_UI`.
- Case 96: device/version information was classified as `FEATURE_OR_UI` instead of `CONTENT_OR_CATALOG`.
- Case 165: iPod Touch and iOS version information was classified as `FEATURE_OR_UI` instead of `CONTENT_OR_CATALOG`.

**Hypothesis:** The taxonomy contains overlapping categories, particularly when customers mention devices, application behavior, or access to content without explicitly stating the underlying issue.

### 3. Technical/device language is over-predicted as PLAYBACK_OR_APP_ISSUE

Examples:

- Case 3: an application complaint was classified as `PLAYBACK_OR_APP_ISSUE` instead of `FEATURE_OR_UI`.
- Case 107: university Wi-Fi information was classified as `PLAYBACK_OR_APP_ISSUE` instead of `FEATURE_OR_UI`.
- Case 194: Windows and Spotify version information was classified as `PLAYBACK_OR_APP_ISSUE` instead of `SUBSCRIPTION_OR_PAYMENT`.

**Hypothesis:** Technical vocabulary such as device, operating system, application, and network terms resembles historical playback/app troubleshooting cases and can pull predictions toward the broad `PLAYBACK_OR_APP_ISSUE` category.

### 4. Sparse inputs produce weak retrieval evidence

Several incorrect cases had low top-1 retrieval similarity:

- Case 12: `0.094`
- Case 107: `0.132`
- Case 63: `0.138`
- Case 166: `0.152`
- Case 87: `0.169`

**Hypothesis:** TF-IDF retrieval depends on lexical overlap. Short or unusually phrased messages contain fewer useful matching terms, reducing the usefulness of retrieved historical examples.

Case 12 is an especially clear example: the customer message was only `Definatly`, while the generated reply introduced an unsupported explanation involving a 30-minute ad-free period.

### 5. Retrieved examples can pull the response toward an incorrect topic

Examples include:

- Case 71: the response assumed a missing A Clockwork Orange soundtrack even though the customer's message did not state that issue.
- Case 96: the response assumed a Stranger Things Easter Egg problem from device/version information.
- Case 179: the response assumed an album/Spotlights association issue not stated in the customer message.

**Hypothesis:** When the current message is ambiguous, the LLM can over-weight an approximately similar retrieved example and treat its topic as the customer's actual problem. Retrieval is therefore useful as supporting evidence but should not be treated as ground truth.

These failure modes explain why the final 44% accuracy should be interpreted as an observed result on a small held-out sample rather than as a general accuracy estimate.

## 17. Limitations

The final system has several known limitations:

* The labelled dataset is relatively small.
* Short or context-dependent customer messages are difficult to classify.
* Several intents have substantial semantic overlap.
* TF-IDF retrieval is lexical and may miss semantically similar cases expressed with different wording.
* Reply quality depends on the quality and relevance of retrieved historical examples.
* The escalation policy is deterministic and intentionally conservative for selected categories.
* The reported 44% intent accuracy is based on a 50-case held-out test set, so it should not be interpreted as a general population accuracy estimate.

These limitations are documented rather than hidden from the evaluation.

---

## 18. Key Design Decisions

The project intentionally avoids unnecessary complexity.

It does not use:

* model fine-tuning
* a vector database
* a complex agent framework
* multiple LLM calls per customer request
* retrieval-threshold-based escalation
* repeated tuning against the held-out test set

The final request path is intentionally simple:

Customer
   |
   v
TF-IDF retrieval
   |
   v
3 historical examples
   |
   v
1 Groq LLM call
   |
   v
Intent + reply
   |
   v
Deterministic escalation

---

## 18.1 What Is Misleading About the Headline Number?

The headline result is:

**44.0% intent accuracy on the 50-case held-out test set.**

This number is an observed accuracy on this particular 50-case sample. It should not be interpreted as a population-level estimate of accuracy across all Spotify support requests.

The test set is intentionally small and was held out from development and prompt/policy tuning. Therefore, the result is useful as a reproducible evaluation of this project configuration, but it should not be generalized beyond the evaluated sample without further testing.

The final agent correctly classified:

**22 / 50 cases**

## 18.2 What We Would Do With One More Week

If an additional week were available, the next iteration would focus on the failure modes observed in the held-out evaluation rather than adding unnecessary system complexity.

1. **Improve conversation-context handling**
   Better distinguish short acknowledgements and follow-up messages whose intent depends on earlier conversation context.

2. **Refine intent boundaries**
   Review development-set examples for the most confused categories, especially `FEATURE_OR_UI`, `CONTENT_OR_CATALOG`, and `PLAYBACK_OR_APP_ISSUE`.

3. **Improve retrieval quality**
   Compare the current TF-IDF retrieval approach with a lightweight semantic retrieval method using the development set only.

4. **Strengthen reply grounding**
   Add stronger safeguards against introducing specific product behavior, policies, features, or account details that are not supported by the current customer context or retrieved evidence.

5. **Expand evaluation**
   Increase the number of held-out examples and continue separate human evaluation of reply quality so that results are less dependent on a small test sample.

## 19. Decision Log

1. **Selected Spotify as the target brand** — Spotify has a substantial set of historical customer-support interactions in the source dataset, making it suitable for building and evaluating a focused support agent.

2. **Used 200 human-labelled examples** — This provides a manageable labelled dataset while satisfying the assignment requirement for a 150–250 example gold evaluation set.

3. **Used nine intent categories** — The categories were designed to cover the recurring types of Spotify support requests while keeping the classification task understandable and explainable.

4. **Used customer-to-Spotify support interactions rather than arbitrary tweet pairs** — This preserves the actual support direction and makes the historical replies useful as evidence for the agent.

5. **Bounded historical conversation context** — Only a limited number of preceding messages are reconstructed so the system retains useful context without creating unnecessarily large prompts.

6. **Used TF-IDF retrieval instead of a vector database** — The labelled problem is small enough that lexical retrieval is simple, fast, transparent, and sufficient for the assignment.

7. **Retrieved the top three historical cases** — Three examples provide multiple pieces of evidence without unnecessarily increasing prompt size or complexity.

8. **Used a hosted pretrained LLM instead of training a new model** — The assignment is focused on building an effective and reproducible support pipeline rather than training a foundation model.

9. **Used structured JSON output from the LLM** — Returning an explicit intent and reply makes the agent output easier to evaluate and integrate into downstream logic.

10. **Kept escalation deterministic** — Escalation rules are easier to inspect, test, and explain than asking a second LLM call to make the operational decision.

11. **Held out 50 cases for final evaluation** — The held-out set provides a separate final check relative to the development work and was not used for prompt or policy tuning.

12. **Grouped the evaluation split by customer ID** — This prevents the same customer from appearing in both development and test data and reduces leakage between the two sets.

13. **Used both a trivial and a simple baseline** — The majority baseline provides a minimal reference point, while TF-IDF + Logistic Regression provides a non-LLM machine-learning comparison.

14. **Evaluated reply quality separately from intent accuracy** — A correct intent does not necessarily produce a useful support response, so reply quality was assessed independently using human and LLM ratings.

15. **Did not treat the LLM judge as ground truth** — Human-vs-LLM agreement was measured explicitly because automated judging can disagree with human assessment. The LLM judge is therefore treated as a secondary signal rather than a replacement for human evaluation.
