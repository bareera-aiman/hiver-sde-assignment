# Spotify Customer Support AI Agent

An explainable customer-support AI pipeline built around historical Spotify support interactions.

The system combines TF-IDF retrieval, a hosted LLM, deterministic escalation rules, and an evaluation framework covering intent classification and reply quality.

---

## 1. Project Overview

The agent takes a customer's current message and optional conversation context and produces:

1. A customer-support intent
2. A concise support reply
3. An escalation decision
4. A reason for that decision
5. Three similar historical Spotify support cases used as evidence

The system does not train a new neural model. It uses a pretrained LLM through the Groq API and augments it with retrieval from historical Spotify support interactions.

### Pipeline

Customer message + conversation context
                |
                v
        TF-IDF retrieval
                |
                v
    Top 3 historical Spotify cases
                |
                v
             Groq LLM
                |
          +-----+-----+
          |           |
          v           v
       Intent       Reply
          |
          v
Deterministic escalation policy
          |
          v
   AUTO_HANDLE / ESCALATE

## 2. Dataset

The project uses the Kaggle Customer Support on Twitter dataset (`twcs.csv`).

The pipeline selects Spotify support interactions and constructs customer-to-Spotify support cases with bounded conversation context.

The derived retrieval corpus is:

`results/spotify_cases.csv`

The construction script is:

`src/build_spotify_cases.py`

The original dataset is stored at:

`data/twcs.csv`

## 3. Human Annotation

A 200-example Spotify dataset was manually labelled for intent.

The final intent categories are:

* `PLAYBACK_OR_APP_ISSUE`
* `SUBSCRIPTION_OR_PAYMENT`
* `ACCOUNT`
* `FEATURE_OR_UI`
* `CONTENT_OR_CATALOG`
* `PROMOTION_OR_EVENT`
* `PRIVACY_OR_DATA`
* `SUPPORT_CHANNEL_OR_LANGUAGE`
* `OTHER`

The completed gold annotations are stored in:

`results/spotify_gold_annotations.csv`

The annotation and merge scripts are:

* `src/annotate_spotify.py`
* `src/merge_annotations.py`

---

## 4. Development / Test Split

The 200 labelled cases are divided into:

* 150 development cases
* 50 held-out test cases

The split uses `StratifiedGroupKFold` with:

* 4 folds
* `random_state=42`
* `customer_id` as the grouping variable

Grouping by customer prevents the same customer from appearing in both development and test sets.

The split is generated by:

`src/create_eval_split.py`

The resulting files are:

* `results/spotify_dev.csv`
* `results/spotify_test.csv`

The 50-case test set used for the final reported evaluation is held out and should not be used for prompt or policy tuning.

## 5. Agent Architecture

### Retrieval

The retriever uses:

* TF-IDF
* unigram and bigram features
* cosine similarity
* top-3 historical cases

Implementation:

`src/retriever.py`

The retrieval corpus is loaded from:

`results/spotify_cases.csv`

### LLM

The final agent uses the Groq API with:

`openai/gpt-oss-20b`

The LLM is instructed to return a structured JSON object containing:

* `intent`
* `reply`

Implementation:

`src/groq_client.py`

### Agent

The main pipeline is implemented in:

`src/agent.py`

It combines retrieval, LLM classification/reply generation, and deterministic escalation.

---

## 6. Escalation Policy

Escalation is deterministic and does not depend on an additional LLM decision.

The current policy is:

| Condition                                      | Action        |
| ---------------------------------------------- | ------------- |
| `PRIVACY_OR_DATA`                              | `ESCALATE`    |
| `ACCOUNT` + configured account-specific action | `ESCALATE`    |
| `OTHER`                                        | `ESCALATE`    |
| Other clear intents                            | `AUTO_HANDLE` |

Configured account-specific actions include requests involving:

* changing email/password
* deleting or closing an account
* refunds
* chargebacks
* cancelling subscriptions
* restoring or recovering an account

Implementation:

`src/escalation_policy.py`

The evaluated 50-case output is:

`results/escalation_test_outputs.csv`

In the final 50-case run:

* 39 cases -> `AUTO_HANDLE`
* 11 cases -> `ESCALATE`

This is an action distribution, not an escalation accuracy measurement, because the human dataset does not contain human-labelled escalation outcomes.

## 10. Run the Final Agent Evaluation

The held-out test set is:

`results/spotify_test.csv`

Run:

```bash
python src/evaluate_agent.py
```

The evaluator is checkpoint-safe. It:

* skips cases already evaluated
* saves every completed case immediately
* limits each run to 30 new API calls by default
* resumes from the existing output
* avoids repeating completed API calls

The per-run limit can be changed when the available API quota permits.

### Windows PowerShell

```powershell
$env:MAX_NEW_CASES_PER_RUN="50"
python src/evaluate_agent.py
```

Output:

`results/agent_test_outputs.csv`

The existing final evaluation contains 50/50 completed cases. The reported result should not be reproduced by repeatedly tuning against the held-out test set.

### Analyze results

After evaluation:

```bash
python src/analyze_agent_results.py
```

## 11. Intent Classification Results

The final held-out evaluation contains 50 cases.

| System                       | Intent Accuracy |
| ---------------------------- | --------------: |
| Majority baseline            |           37.0% |
| TF-IDF + Logistic Regression |           34.5% |
| Retrieval + LLM agent        |       **44.0%** |

The final agent correctly classified:

**22 / 50 test cases**

The 44% result is the official held-out evaluation result.

Detailed results:

`results/agent_test_outputs.csv`

---

## 12. Failure Analysis

The final evaluation identified several recurring failure modes:

1. Short contextual messages are difficult to classify without sufficient context.
2. `FEATURE_OR_UI` and `CONTENT_OR_CATALOG` are frequently confused.
3. Technical-looking messages can be over-predicted as `PLAYBACK_OR_APP_ISSUE`.
4. Sparse messages can produce weak retrieval evidence.
5. Retrieved examples can sometimes influence the response too strongly when they are only approximately similar.

The analysis is generated by:

`src/analyze_agent_results.py`

## 13. Reply Quality Evaluation

Reply quality was evaluated separately from intent classification.

A fixed sample of 40 cases was selected from the existing 50 generated test outputs.

The five human evaluation criteria were:

* Correctness
* Relevance
* Grounding
* Actionability
* Communication

Each criterion was rated from 1 to 5, along with an overall score.

The fixed evaluation sample is:

`results/reply_quality_evaluation.csv`

Human evaluation:

`results/reply_quality_evaluation_human.xlsx`

Human overall mean:

**4.175 / 5**

---

## 14. LLM Reply Judge

The same 40 existing generated replies were also evaluated by an LLM judge.

The judge did not regenerate the agent replies.

Output:

`results/reply_quality_llm_judgments.csv`

LLM judge overall mean:

**4.150 / 5**

Human-vs-LLM agreement is analyzed in:

`results/reply_quality_agreement.csv`

Overall exact agreement:

**42.5%**

Overall agreement within one rating point:

**72.5%**

The agreement analysis indicates that similar average scores do not imply strong case-level agreement. Communication had substantially stronger agreement than the other criteria.

## 15. Reproducibility

Important evaluation artifacts are checkpointed and stored in `results/`.

The final agent evaluation should not be repeatedly rerun merely to improve the score.

The intended workflow is:

Human-labelled data
        |
        v
150 development / 50 test
        |
        v
Develop and analyze using DEV
        |
        v
Freeze final agent
        |
        v
Evaluate held-out TEST
        |
        v
Analyze results

The final test set should remain unchanged after the reported evaluation.

## 17. Limitations

The final system has several known limitations:

* The labelled dataset is relatively small.
* Short or context-dependent customer messages are difficult to classify.
* Several intents have substantial semantic overlap.
* TF-IDF retrieval is lexical and may miss semantically similar cases expressed with different wording.
* Reply quality depends on the quality and relevance of retrieved historical examples.
* The escalation policy is deterministic and intentionally conservative for selected categories.
* The reported 44% intent accuracy is based on a 50-case held-out test set, so it should not be interpreted as a general population accuracy estimate.

These limitations are documented rather than hidden from the evaluation.

---

## 18. Key Design Decisions

The project intentionally avoids unnecessary complexity.

It does not use:

* model fine-tuning
* a vector database
* a complex agent framework
* multiple LLM calls per customer request
* retrieval-threshold-based escalation
* repeated tuning against the held-out test set

The final request path is intentionally simple:

Customer
   |
   v
TF-IDF retrieval
   |
   v
3 historical examples
   |
   v
1 Groq LLM call
   |
   v
Intent + reply
   |
   v
Deterministic escalation
